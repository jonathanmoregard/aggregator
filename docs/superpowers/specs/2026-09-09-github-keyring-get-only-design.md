# GitHub ingest: keyring credential behind a GET-only capability

Date: 2026-09-09
Status: approved

## Problem

`aggregator-ingest.service` exports an agenix-managed read-only GitHub PAT as
`GH_TOKEN`. That token expired on 2026-09-01. GitHub ingest has failed 56
consecutive times, leaving its high-water mark at 2026-08-31 and producing
repeated failure notifications. Every other ingest source remains healthy.

The machine already has a working GitHub CLI OAuth credential in its keyring.
A transient user-manager probe successfully read it and GitHub returned HTTP
200. The timer nevertheless hides that credential behind the expired PAT.

The static PAT is the wrong ownership model: it duplicates a credential,
expires independently, and requires recurring manual replacement. The prior
scope gate protects against a write-capable token by inspecting OAuth scopes,
but protects the credential rather than constraining what this program can do.

## Decision

Use the GitHub CLI keyring as the single credential owner. Constrain the
aggregator's GitHub subprocess boundary to the capability it needs:

- only GitHub search endpoint paths generated by `GitHubSource` are accepted;
- every API invocation explicitly selects HTTP `GET`;
- paths are passed as one subprocess argv value, never through a shell;
- unexpected paths fail before `gh` starts;
- subprocess, authentication, response, and JSON failures remain loud and
  preserve the existing source watermark.

OAuth scopes remain visible through `aggregator github-token-status`, but
write-capable scopes no longer block ingestion. `AGGREGATOR_ALLOW_WRITE_TOKEN`
is removed: a runtime escape hatch is unnecessary once the code boundary is
GET-only.

## Alternatives rejected

1. Regenerate the read-only PAT. Small diff, but repeats the expiry and
   duplicate-credential failure by design.
2. Create a GitHub App with rotating read-only installation tokens. Strong
   least privilege, but introduces another credential owner, private-key
   lifecycle, and more upkeep than this single-user local index warrants.

## Aggregator changes

`aggregator/sources/github.py` will:

1. validate API paths against the fixed `/search/issues?` surface before
   subprocess execution;
2. invoke `gh api` with explicit method `GET`;
3. stop calling the scope-enforcement gate from `iter_records`;
4. keep token scope reporting as diagnostics, with recommendations describing
   GET-only enforcement instead of requiring a second PAT;
5. remove the override behavior and documentation.

Tests will first prove the current failure, then pin:

- a keyring credential with `repo`, `gist`, and `workflow` scopes can ingest;
- generated API subprocess argv explicitly requests `GET`;
- non-search, flag-shaped, and control-character paths are rejected without
  starting a subprocess;
- authentication/API failures still surface as ingest errors;
- tokens never appear in logs, exception text, or argv.

No search query, record shape, watermark, retry, or notification behavior
changes.

## NixOS changes

A dedicated worktree under `~/Repos/nixos-config-worktrees/` will:

1. pin `aggregator-src` to the reviewed aggregator commit;
2. remove the wrapper's read/export of `github-readonly-pat`;
3. remove the host's `age.secrets.github-readonly-pat` declaration;
4. add `github-readonly-pat` to the dead-credential eval guard, naming the
   GitHub CLI keyring as owner;
5. update comments, failure text, and `vm-base` assertions to match the new
   credential flow.

The encrypted `.age` file will not be deleted in this task. It becomes unused
and can be removed later with explicit deletion approval.

The timer remains a user unit, so it reaches the same desktop keyring as the
successful transient user-manager probe. Its `gh` binary remains pinned from
Nix store `runtimeInputs`; PATH cannot substitute another executable.

## Verification and deployment

Aggregator gate:

- focused RED/GREEN tests for GitHub source and token status;
- ruff on changed Python;
- full project test suite.

NixOS gate:

- RED/GREEN assertions in `tests/base.nix` and
  `tests/secrets-no-dead-credentials.nix`;
- flake evaluation and generated Home Manager closure inspection;
- `nix build .#checks.x86_64-linux.secrets-no-dead-credentials -L`;
- `nix build .#checks.x86_64-linux.vm-base -L`;
- interactive feature-VM smoke for the changed multistep wrapper, including
  its no-credential failure path;
- real-host invocation of the built wrapper through the user manager, proving
  the keyring success path before PR handoff.

Deployment order:

1. aggregator PR passes and is merged;
2. NixOS PR, pinned to that reviewed commit, passes and is merged;
3. push-to-main auto-deploy updates the live unit;
4. run one ingest tick and verify GitHub watermark advances, service exits 0,
   and no failure notification fires.

## Security properties

- no new secret is created, copied, printed, or stored in the Nix store;
- GitHub token stays in its existing keyring owner;
- the GitHub adapter exercises authority only through a pinned `gh` subprocess
  whose operation and endpoint are checked before execution;
- GitHub response content remains untrusted input and follows existing record
  validation/error isolation;
- failure stays loud and watermarks stay untouched on partial or total loss.
